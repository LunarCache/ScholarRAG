# A24：跨进程空间与用户公平调度

实施日期：2026-10-27。基于拉取后的 `3593e31`，继续 A21–A23 的三类持久化 Worker；本项是调度改造，整体生产计划仍在实施中。

## 问题与用户可见变化

问答、摄取、评测之前都按全局创建时间领取。某空间先提交一批任务，其他空间后来提交的在线任务会排在整批旧任务之后。同一空间内也存在单个用户占满前排的问题。

现在每类队列分别按以下顺序选择可领取任务：

1. 最近较久未获调度的工作空间；从未获调度的空间优先。
2. 该空间内最近较久未获调度的用户；从未获调度的用户优先。
3. 同一空间、同一用户内按创建时间排序；时间相同则按任务 ID 确定顺序。

例如 A 先提交 A1、A2、A3，B 随后提交 B1、B2，持续领取顺序为 A1、B1、A2、B2、A3。同一空间增加用户不会增加该空间的调度份额。该规则默认生效，无需新增环境变量或浏览器操作。

这是按**领取次数**实现的非抢占调度。已经执行或持有有效租约的任务继续占用当前槽位，新任务等待下一个可用槽位；不同长度任务的 CPU 时间、供应商时间和费用没有等份保证。

## 实现与事务边界

- `storage/scheduling.py`：共享选择逻辑、持久化逻辑时钟与最近获调度记录。
- `rag/runs.py`、`ingestion/workspaces.py`、`evaluation/jobs.py`：保留各自原有可领取条件，将全局 FIFO 替换为分层选择。
- `storage/identity.py` 和 `QueryRunStore` 初始化：幂等创建调度辅助表，覆盖独立使用摄取队列及本地问答存储的初始化路径。

新增辅助表：

| 表 | 内容 |
| --- | --- |
| `queue_scheduling_clocks` | 每类队列单独递增的逻辑轮次 |
| `queue_scheduling_turns` | 每类队列、空间、用户最后获得领取的轮次；空用户键仅用于空间汇总 |

选择候选、推进逻辑轮次、更新空间/用户记录，以及现有租约写入，都位于同一个 `BEGIN IMMEDIATE` 事务。租约写入失败时调度记录一起回滚；无可领取任务时不推进轮次。多个进程读取同一 SQLite 数据库，进程重启不会重置顺序。

有效租约仍排除在候选之外；过期任务按同一调度规则重新领取，并继续走 A21–A23 的检查点与保守恢复逻辑。取消和终态任务不消耗领取轮次。恢复领取也计一次轮次，避免某个反复失效的任务始终占据队首。

调度器只接收服务端固定 SQL；身份、空间与所有者来自已持久化的任务。没有新增跨用户读取接口或放宽授权。Worker 领取后仍必须验证当前会话、成员、文档范围和租约。

## 兼容性、迁移与回滚

本项只新增两个内部辅助表，不修改现有任务、事件、产物、API 或身份 Schema v5。已有 v5 开发库在初始化时自动增加辅助表；A22 对更旧摄取 Schema 的拒绝规则仍然有效，本项不会迁移、清除旧任务或默认数据。

部署时统一升级 API 与三类 Worker。混用旧 Worker 会同时存在 FIFO 领取和轮转领取，不能保证统一公平性。回滚前停止新版 Worker，再运行上一版本；上一版本会忽略辅助表，任务与租约格式保持兼容。保留辅助表可在再次升级时延续历史轮次。数据库修改前仍应按现有部署流程备份。

辅助表每个实际调度过的空间和用户保存一条记录，不按任务累积。用户或空间删除时的记录清理尚未实现，也不应通过定时清空记录重置公平顺序。

## 验收

`tests/test_queue_fairness.py` 将以下 9 组场景分别用于问答、摄取和评测，共 **27 项**离线回归：

- 晚到空间在旧积压未清空时获得轮次；同用户内部仍按顺序领取。
- 空间内用户轮转；更多用户不会扩大该空间相对其他空间的领取份额。
- 第一个任务已领取后新空间入队，获得下一个可用轮次。
- 有效租约不被重复领取，过期租约恢复遵守同一轮转。
- 已取消积压不消耗调度轮次。
- 注入租约写入失败，验证调度时钟与租约一起回滚。
- 四个并发客户端领取六个任务，无重复领取，时钟只前进六次。
- 两个独立 Python 子进程先后领取，进程退出后仍延续空间轮转。
- 一类队列的积压和调度记录不影响另一类队列。

## 剩余边界与下一步

- 各队列独立轮转，没有跨三类队列的统一优先级或供应商全局容量控制。
- 没有费用预算、预留、结算、RPM/TPM 或跨进程供应商并发令牌；现有队列准入上限继续生效。
- 已运行任务不被抢占，没有按空间硬性限制运行中的总任务数；若其他空间在槽位已占满后到达，仍需等待槽位释放。
- 轮转不等价于按耗时或费用的加权公平；没有生产吞吐、P95 或超大租户数压测结果。候选选择需扫描符合条件的积压并排序，需根据真实容量继续评估。
- 下一项优先建立任务预算与费用预留/结算，再接入跨进程供应商容量和速率控制；OIDC、解析审核权限、PostgreSQL、对象存储与恢复演练仍未完成。
